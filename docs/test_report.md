## 7. Что получилось хорошо ✅

- Полноценный end-to-end тест: `place_id` из POST прокидывается во все последующие запросы — цепочка работает корректно
- Хорошее разделение ответственности: `api.py` — вызовы, `cheking.py` — проверки, `http_methods.py` — транспорт
- Allure-аннотации (`@allure.epic`, `@allure.description`) дают читаемые отчёты
- Проверка после DELETE подтверждает необратимость удаления: сервер возвращает `404` + слово `"failed"` в сообщении
- Адрес реально обновляется — подтверждается повторным GET после PUT

## 8. Что можно улучшить 🔧

| # | Проблема | Рекомендация |
|---|---|---|
| 1 | Все шаги в одном тесте | Разделить на тест-функции с `conftest.py`-фикстурами |
| 2 | Нет негативных сценариев | Добавить: невалидный `place_id`, без API-ключа, пустой body |
| 3 | Данные захардкожены в `api.py` | Вынести в `test_data.py` или `conftest.py` |
| 4 | API-ключ в открытом виде | Использовать `os.getenv("API_KEY")` |
| 5 | Нет проверки типов данных | Добавить `jsonschema` для валидации схемы ответа |
| 6 | Нет параметризации | Применить `@pytest.mark.parametrize` |

## 9. Ретроспектива

### 🎯 Keep Doing — продолжать

- Разделять логику на слои (API / HTTP / проверки) — это правильная архитектура
- Использовать Allure для наглядных отчётов
- Проверять данные после каждого изменяющего запроса (PUT → GET)

### 🔧 Start Doing — начать

- Писать негативные тест-кейсы
- Добавить `conftest.py` с фикстурами создания/удаления локации
- Настроить GitHub Actions с публикацией Allure-отчёта

### 🛑 Stop Doing — прекратить

- Хранить API-ключи прямо в коде — использовать переменные окружения
- Объединять несколько логических шагов в один тест без возможности изолированного запуска
